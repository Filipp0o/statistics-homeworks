From mnemonic to Ethereum address

Understand key derivation, public-key cryptography, hashing, encoding and checksums in an Ethereum HD wallet.

Each stage serves a different purpose

This pipeline describes key-controlled Ethereum accounts in an HD wallet using these standards. Not every wallet or account type follows the same pipeline.

01 · BIP-39

Entropy → mnemonic → seed

Generation starts with entropy produced by a cryptographically secure random generator. BIP-39 encodes 128 to 256 entropy bits and a short SHA-256 checksum as 12, 15, 18, 21 or 24 words from a 2048-word list. A 12-word mnemonic represents 128 entropy bits and a 4-bit checksum. [2]

The seed is derived with PBKDF2-HMAC-SHA512: the mnemonic is the password, the salt is "mnemonic" concatenated with an optional passphrase, the iteration count is 2048, and the output is 64 bytes. The mnemonic and passphrase use UTF-8 NFKD normalization. A different passphrase produces a different seed; an absent passphrase is an empty string. A wallet app’s local password can protect stored data without changing the seed. [2]

02 · BIP-32 and BIP-44

Seed → private key

BIP-32 applies HMAC-SHA512 to the seed with the key "Bitcoin seed". The first 32 bytes determine the master private key, and the remaining 32 bytes become its chain code. An extended key consists of a key and its chain code. Child keys are derived deterministically using the parent key, chain code and child index. [3]

Hardened derivation, marked with an apostrophe, requires the parent private key. Nonhardened derivation also allows child public keys to be derived from an extended public key. The chain code is derivation material, rather than an address or password. BIP-32 specifies checks for invalid derived keys. [3]

BIP-44 assigns meanings to the levels of the key tree: purpose, coin type, account, change and address index. It organizes BIP-32 derivation without introducing a new hash algorithm. A common path for the first Ethereum address is m/44'/60'/0'/0/0. The value 60 identifies Ethereum in SLIP-44. Different paths produce different keys, and wallet conventions may vary. [4, 6]

03 · secp256k1

Private key → public key

The private key is a scalar k from 1 to n − 1, where n is the order of the generator. Q = kG is computed on secp256k1, whose equation is y² = x³ + 7 over a very large finite field. The private key is used for ECDSA signatures and the public key for verification. This operation establishes a key pair; it is not hashing. [1, 7]

04 · Keccak-256

Public key → hash

The uncompressed public key is represented by 32 bytes for x and 32 bytes for y. Keccak-256 hashes the 64 bytes x || y, excluding the initial 0x04 byte of SEC 1 serialization. The last 20 bytes of the digest become the 160-bit address, represented by 40 hexadecimal characters with a 0x prefix. [5, 8]

05 · Hexadecimal encoding

20 bytes → readable address

The 160 address bits become 40 hexadecimal characters, prefixed with 0x. Encoding represents the same data; it does not add secrecy.

06 · EIP-55

Address → visible checksum

EIP-55 hashes the lowercase hexadecimal address string without 0x, interpreted as ASCII text, using Keccak-256. A letter a–f is capitalized when the corresponding hexadecimal digit of the hash is at least 8; numeric digits remain unchanged. The binary address is identical. The checksum helps detect typing errors without authenticating the recipient. [9]

Generation, derivation, hashing, checksums and encoding

OperationPurpose
GenerationIntroduces fresh randomness, such as the initial entropy.
DerivationDeterministically obtains keys from a seed and a path.
Public key cryptographyRelates k and Q and supports signing and verification.
HashingMaps data to a fixed-length digest.
ChecksumProvides a check against some transcription errors.
EncodingRepresents data as words, bytes or hexadecimal characters.

BIP-39 combines encoding, a checksum and derivation. BIP-32 uses a construction based on HMAC, while EIP-55 combines hashing with encoding. A standard can therefore use several primitives without being identical to one primitive.

The change level is retained for BIP-44 compatibility. In an account-based Ethereum wallet it does not represent UTXO transaction change. Reproducing the same account requires the correct mnemonic, passphrase and derivation path.

Why the pipeline uses different techniques

A wallet solves several different problems. Entropy generation supplies the initial secret material; BIP-39 makes it manageable as a mnemonic and derives a seed. BIP-32 reconstructs many keys from one backup, while BIP-44 provides an organized way to locate a particular key.

secp256k1 provides the mathematical relationship between private and public keys and supports digital signatures. Keccak-256 hashes the public key so that an address can be derived. EIP-55 uses another hash calculation to encode an error check in the written address. No single algorithm, by itself, supplies fresh randomness, key hierarchy, signatures, address derivation and error detection.

The mapping k → kG is easy to compute forward and, for properly chosen real-world parameters, difficult to invert. Irregular-looking points are not the reason for its security. Likewise, address histograms describe the sample but do not establish preimage or collision resistance.

Interpreting the statistical results
The sample is consistent with an approximately uniform appearance. It does not prove randomness, independence or security. Derivation is deterministic, and a 512-bit seed derived from 128 entropy bits does not automatically contain 512 bits of entropy. A deterministic function does not create additional entropy.
Mnemonic words are not independent because they incorporate a checksum. Public-key coordinates are constrained by the curve. Addresses reflect a hash digest truncated to 160 bits. EIP-55 changes only the representation: capitalization does not add new random bits to the underlying address.

 
SHA-512 and Keccak are not interchangeable
SHA-512 belongs to the SHA-2 family and is used in PBKDF2 and HMAC for derivation. Keccak is a different design, based on the sponge construction, selected by NIST for SHA-3.
Ethereum uses Keccak-256, which differs from SHA3-256: padding and domain separation change the result. Replacing it with SHA3-256 produces a different address.
Historical order
RSA: introduced in 1977, with the journal paper in 1978. SHA-2/SHA-512: proposed in 2001 and standardized in FIPS 180-2 in 2002. BIP-32: 2012. BIP-39: 2013. BIP-44: 2014. SHA-3: 2015. EIP-55: 2016.
The assignment simplifies the SHA-2 date to 2001; the final NIST standard dates to 2002. The BIPs originated in Bitcoin and were later reused by many Ethereum wallets.
